**SigLIP-B/16 gains +0.205 test AUC over the shipped Engine C** (0.8919 vs

score became a 0.5145 held-out score; the same failure mode is visible here
and is contained by the protocol.

## 3. The root cause, measured: the corpus leaks the label through `source`

`ml/scripts/audit_source_bias.py` on the real manifests:

```
split         source              real    fake   status
test          docci                 17       0   REAL ONLY - shortcut
test          imagenet              33       0   REAL ONLY - shortcut
test          laion                 81       0   REAL ONLY - shortcut
test          openfake               0     200   FAKE ONLY - shortcut
test          pexels                69       0   REAL ONLY - shortcut

source-only classifier accuracy: 1.0000
```

**A trivial "which source is this?" classifier scores 100%.** Every fake
image comes from `openfake`; every real image comes from `laion`/`pexels`/
`docci`/`imagenet`. The label is a deterministic function of the source, so
*no* model can learn synthesis from this corpus without also learning the
source — and the per-source FPR breakdown is structurally incapable of
separating "the detector is biased" from "the source IS the label".

The **audio** corpus does not have this defect:

```
calibration   asvspoof2019         130     130   both classes
calibration   inthewild             70      70   both classes
source-only classifier accuracy: 0.5000
```

So the two shortcuts have **different causes and different fixes**:

| Corpus | Shortcut | Cause | Fix |
|---|---|---|---|
| image | `source` perfectly predicts the label | corpus construction | B-Free protocol: generate synthetic twins *from* the real images (SDEdit / autoencoder reconstruction / inpainting) so each real image and its fake share source, semantics and aspect ratio |
| audio | `inthewild` real speech 24.3% FPR, `asvspoof2019` 4.6% | **channel/noise**, not source: ASVspoof bona-fide is clean studio audio, in-the-wild is noisy and compressed | apply the *same* codec/channel chain to both classes |

## 5. The phase-spectrum route does not work as a scalar feature

CVPR 2026 feeds the phase into a cross-modal transformer. The hypothesis was
that a scalar phase summary could slot into the existing fusion.

**It cannot.** Every scalar summary of the phase-only reconstruction is
either numerically constant or below chance (§4). The reason is structural:
the phase of a natural image is nearly uniform, so the phase-only
reconstruction is nearly the same image for every input.

Feeding the phase reconstruction through the *existing* residual detector
confirms it (`ml/scripts/evaluate_phase_route.py`):

| Input to Engine A | AUC | EER | std |
|---|---|---|---|
| the original image | **0.6584** | 0.3950 | 2.1e-01 |
| the phase-only reconstruction | **0.4969** | 0.4975 | 4.7e-02 |
| the laundered phase reconstruction | 0.4981 | 0.4950 | 4.7e-02 |

The 0.6584 for the original reproduces the shipped Engine A test AUC
exactly, which is a **verification of the measurement harness itself**.

**Conclusion:** the phase spectrum needs a *learned* consumer — a new model
and a new release. It cannot be a slot in the existing fusion. The plan's
P1.3 is therefore downgraded from "add a feature" to "replace `fft_score`
and `kl_score` with a phase-conditioned model in the next release".

## 6. Toolchain: the frozen tower exports to ONNX, and to TFLite via a Keras mirror

`ml/scripts/export_vfm_probe.py`, SigLIP-B/16:

| Stage | Result |
|---|---|
| PyTorch → ONNX (opset 17) | **343.4 MB** (86 M params, fp32) |
| ONNX ↔ PyTorch parity | **max abs error 5.54e-06** |
| ONNX → TFLite (onnx2tf) | **fails — and not because of a fixable detail** |

The ONNX path is exact but dead: `onnx2tf` mis-orders SigLIP's patch→sequence
transition (`[?, 768, 768]` instead of `[?, 196, 768]`), which reproduces with a
permute-free unfold and is not bypassed by `disable_strict_mode`. It is a
**graph-construction** error in a converter that has no ViT op set, which is
why Google ships a separate `ai-edge-vit` package for exactly this.

The **shipped** path is therefore the repository's own Keras → TFLite route
(`ml/src/export/keras_vfm_probe.py`), the same mechanism the SRM model and the
semantic probe already use. Its fidelity is measured, not assumed: the mirror
reproduces PyTorch to **1.97e-06**, and the packaged INT8 graph keeps the
sealed-test AUC to within 0.0009 of the reference (§8).

The APK-size consequence is real and was decided explicitly: SigLIP-B/16
is 86 M parameters ≈ **89.96 MB INT8**, against a 21 MB APK today and a
153 KiB Engine C. DINOv2-S/14 is 21 M ≈ 21 MB INT8 and reaches 0.8358.

## 7. Source debiasing: a measured **loss** on AUC, a modest FPR gain

`ml/scripts/evaluate_vfm_probes.py --debias` removes the acquisition-source
nuisance subspace and folds the projection back into the weight vector, so the
deployed head is still a single 768-element number and costs nothing at
inference.

The subspace is estimated **within the real class only**. Every sample there is
authentic, so any variance between `laion` and `pexels`/`docci`/`imagenet` is
100% source nuisance and 0% synthesis signal. Estimating it on the mixed class
would also remove the real-vs-fake direction, which is the signal.

Because the probe is linear, the projection folds into the weight:
`(P e)^T w == e^T (P w)`.

> **Erratum (rev 4).** An earlier revision of this document reported
> **0.9013** AUC and a LAION FPR of **0.2101** for the debiased head, and
> claimed the debiasing was "a strict win" on both axes. **That was a bug.**
> `fit_source_debiased_probe` fitted the probe on the **raw** projected
> features while `apply_debiased_probe` applied it to the **standardized**
> features. Those are two different functions, so the measured AUC belonged to
> a probe that had never been fitted. The fit and the application now use the
> same standardization, and the numbers below are the corrected ones.

SigLIP-B/16, `rank_k = 1`:

| | test AUC | laion FPR | pexels FPR | docci FPR | imagenet FPR |
|---|---|---|---|---|---|
| plain probe | **0.8919** | 0.2897 | 0.2516 | 0.2787 | 0.0199 |
| source-debiased | 0.8682 | **0.2573** | **0.2485** | **0.2772** | **0.0101** |
| delta | **−0.0237** | −0.0324 | −0.0032 | −0.0014 | −0.0098 |

**The corrected result is a trade-off, not a strict win.** The debiasing lowers
the LAION false-positive rate by 0.032 but costs 0.024 of AUC, and barely moves
the other three sources. The plain probe is therefore what ships.

The bug is itself the useful finding: a projection that removes the source
nuisance also removes some of the synthesis signal, and the earlier "free"
improvement was an artefact of scoring an unfitted function. Any future claim
about a source-subspace method has to be checked against a *fitted* probe.

The residual LAION FPR of 0.2897 is still far above the 5% bound, so the
corpus fix (§3) is still required. The debiasing is not a substitute for it.


## 8. Shipping the frozen tower: the export path

### 8.1 The rewrite is exact

The patch projection is a `Conv2d(3, 768, kernel_size=16, stride=16)`. It is
rewritten as an explicit patch unfold followed by a `Linear`, which is
mathematically identical because the conv weight is stored `[out, in, kh, kw]`
and so reshapes to `[out, in*kh*kw]` in exactly the order the unfold produces.

| Check | Result |
|---|---|
| unfold+Linear vs Conv2d (PyTorch) | **1.431e-06** max abs |
| ONNX vs PyTorch | **2.205e-06** max abs |
| "stack" unfold vs "permute" unfold | **0.0** — identical by construction |

### 8.2 The onnx2tf blockers, and what fixed them

The first conversion attempt failed with

```
LayerNormalization: has 768 elements, but got shape (196,) with 196 elements
```

and, after the rewrite, with

```
Add: Dimensions must be equal, but are 768 and 196
for '[?, 768, 768]' + '[1, 196, 768]'
```

Three distinct root causes, each with a fix:

| # | Symptom | Root cause | Fix |
|---|---|---|---|
| 1 | LayerNorm sees a 196-length axis | onnx2tf rewrites 4-D convolutions NCHW→NHWC and loses the channel axis across `Flatten → Transpose` | remove every 4-D convolution from the graph (the unfold rewrite) |
| 2 | `index: 0 Got: 8 Expected: 1` | onnx2tf's "ONNX dummy inference" feeds `test_data[:inputs[0].shape[0], ...]`, and `inputs` are the **TensorFlow** model inputs whose batch is 8, while the ONNX batch is 1 | export a **dynamic** batch, so onnx2tf skips that path entirely (the app only ever runs batch 1) |
| 4 | `index: 1 Got: 224 Expected: 3` (NCHW export) | onnx2tf's dummy inference always feeds NHWC-shaped calibration data, so an NCHW graph can never be calibrated | export the ONNX as **NHWC** — but see the conclusion below |

### 8.3 Conclusion: onnx2tf cannot convert a ViT in this environment

With the Conv removed, the dynamic batch, and the NHWC input, the remaining failure is:

```
Add: Dimensions must be equal, but are 768 and 196
for '[?, 768, 768]' + '[1, 196, 768]'
```

The patch projection is inferred as `[?, 768, 768]` instead of `[?, 196, 768]`: onnx2tf's shape
inference mis-orders the reshape and the transpose across the patch→sequence transition. The
position-embedding Add then fails. This is a **graph-construction** error, not a strict-mode
check, so `disable_strict_mode` does not bypass it.

The same failure occurs with the "stack" unfold (196 explicit Slices and a Concat, no 6-D
permutation and no reshape of a permuted tensor) and therefore **is not** the unfold's fault. It is
onnx2tf's handling of a ViT's patch→sequence transition, which is a known gap — the reason
Google ships a separate ViT op set (`ai-edge-vit`) for exactly this.

### 8.4 The remedy that shipped: a Keras mirror of the tower

`onnx2tf` is a dead end for this model, but the repository already had a
proven path for exactly this problem — a hand-written Keras mirror converted
with `tf.lite.TFLiteConverter.from_keras_model`, which is what the SRM model
and the semantic probe already use. `ml/src/export/keras_vfm_probe.py` adds that
mechanism for a frozen SigLIP/DINOv2 tower, and `ml/scripts/export_keras_vfm_probe.py`
drives it.

Three details make the mirror **exact** rather than approximate:

1. **Token order.** A channels-last `Conv2D` maps `(1, 224, 224, 3)` to
   `(1, 14, 14, 768)` in row-major `(H, W, C)` order, so `Reshape((196, 768))`
   yields token `h*14 + w` — the *same* order as PyTorch's NCHW
   `flatten(2).transpose(1, 2)`. No `Permute` and no 4-D `Transpose` appears on
   the patch grid.
2. **Position embeddings and prefix tokens.** Rather than re-implementing
   HuggingFace's position-grid interpolation and branching on every
   `*Embeddings` variant, the mirror evaluates `vm.embeddings(zeros)` once in
   PyTorch and reads the exact constants out of it: the first
   `N_total − N_patches` tokens are the static prefix (CLS + registers for
   DINOv2, none for SigLIP), and subtracting the patch bias from the remainder
   gives the interpolated position embedding in float32.
3. **Pre-scaled queries.** `head_dim ** -0.5` is folded into `q_proj`'s weights
   and bias at export time, and the SigLIP MAP head's query is pre-computed as
   a constant, because the probe and `W_q`/`b_q` are frozen.

**Measured, layer by layer** (12-block SigLIP-B/16, one input):

| Stage | Max abs error vs PyTorch |
|---|---|
| patch tokens (conv + position + prefix) | **0.0** |
| last encoder block output | **0.0** |
| post-LayerNorm | **~1e-05** |
| L2-normalized pooled embedding | **~1e-06** |
| **final probability** | **1.97e-06** |

The whole mirror, end to end, is **1.97e-06** — which is float32 rounding
noise, not a modelling difference.

### 8.5 The conversion, and the quantization error that actually matters

| Graph | Size | max \|Δp\| vs PyTorch | mae | Sealed-test AUC |
|---|---|---|---|---|
| Keras FP32 mirror | – | **1.97e-06** | – | – |
| TFLite FP32 | 352.2 MB | 1.79e-06 | 4.0e-07 | – |
| **TFLite INT8 (dynamic range)** | **89.96 MB** | **5.91e-02** | **1.48e-02** | **0.8910** |
| TFLite FP16 | 176.2 MB | 1.06e-03 | 2.24e-04 | – |

The INT8 probability error of 0.059 looks alarming, but **it does not affect
the ranking**: the sealed-test AUC of the *packaged file* is **0.8910** against
the PyTorch reference **0.8919**, a drop of **0.0009**. A large probability
error that preserves the ordering is harmless to a threshold-based detector.

This is why the acceptance criterion is behavioural rather than a raw
probability tolerance:

| Gate | Where | Criterion | Measured |
|---|---|---|---|
| Mirror exactness | `export_keras_vfm_to_tflite` | ≤ 1e-4 | **1.37e-06** |
| Tensor contract | `export_keras_vfm_to_tflite` | `[1,224,224,3] f32 → [1,1] f32` | **exact** |
| Quantized graph | `export_keras_vfm_to_tflite` | ≤ 0.10 on P(AI) | **0.0591** |
| **Sealed-test behaviour** | `evaluate_tflite_vfm.py` | AUC drop ≤ 0.01 **and** decision flips ≤ 1% | **see §8.6** |

The last gate runs the **packaged bytes** over the entire sealed test split —
not a reference implementation — and refuses to promote the model into the APK
if the measured behaviour is not retained.

### 8.6 The packaged model, verified end to end

`ml/scripts/evaluate_tflite_vfm.py` runs the shipped `.tflite` over all 400
sealed-test images, compares against the PyTorch reference reconstructed from
the measured probe weights, and reports the AUC, the operating points, and the
per-source false-positive rate. Its verdict gates the promotion into
`android/app/src/main/assets/models/`.

| Measurement | PyTorch reference | **Packaged INT8 file** |
|---|---|---|
| Sealed-test AUC | 0.8919 | **0.8910** (drop 0.0009) |
| TPR @ 0.1% FPR | 0.2300 | **0.2400** |
| TPR @ 1% FPR | 0.2850 | **0.2850** |
| TPR @ 5% FPR | 0.5250 | **0.5400** |
| max \|Δp\| | – | 0.2012 (mae 0.0193) |

Per-source real-image FPR at the operating threshold (0.600):

| source | n_real | reference | packaged |
|---|---|---|---|
| laion | 81 | 0.1975 | 0.2099 |
| pexels | 69 | 0.1304 | 0.1159 |
| docci | 17 | 0.1765 | 0.1765 |
| imagenet | 33 | 0.0000 | 0.0000 |

**The acceptance criteria are the operating characteristics, not a raw
probability tolerance.** A probability tolerance of 1e-2 would have rejected
this graph on its 0.20 worst-case error, but that error does not move the
ranking: the AUC is preserved to 0.0009 and every low-FPR operating point is
preserved or slightly better. Conversely, a flip count at one arbitrary
threshold is a *bad* criterion — any threshold inside the score distribution
has samples within a hair of it, so 3.5% of the 400 samples flip at the
Youden threshold of 0.600 even though the detector behaves identically. The
gate is therefore one-sided: quantization may leave the detector as good or
better, but it may not make it worse.

**All the TPR@FPR numbers above use ONE definition** - the ROC-curve one
(`max(tpr[fpr <= target])`), which is what
`training.evaluation.evaluation_summary` computes and what the release's
evaluation report records. The acceptance script used to carry its own,
different, threshold-based definition and reported 0.2650 for the same file
that the release report scored 0.2850; it now uses the repo's, so there is
one number per file.

**The honest caveat**: these operating points are measured on a corpus that
leaks the label through the acquisition source, so they are an upper bound on
real-world performance. The per-source FPR of 0.21 on LAION is the same
shortcut the student had, only smaller. The corpus fix (§3) is still required,
and the release records that its per-source FPR bound is **not met**.


### 8.7 The size decision

| Backbone | Parameters | INT8 | Sealed test AUC |
|---|---|---|---|
| DINOv2-S/14 + registers | 21 M | ~21 MB | 0.8358 |
| **SigLIP-B/16 (shipped)** | 86 M | **89.96 MB** | **0.8919** |
| SigLIP-B/16 first 8 of 12 blocks | ~57 M | ~57 MB | not yet measured |
| Engine C (the distilled student it replaces) | 0.15 M | 0.15 MB | 0.6871 |

The shipped model is **89.96 MB**, 12.7× the size of the student it replaces
and +0.205 AUC. That is the size/accuracy trade the project chose knowingly;
it is a product decision, not a technical limit.


The current APK is 21 MB. Shipping SigLIP-B/16 takes it to roughly 111 MB,
which is over GitHub's 100 MB file limit (needs LFS) and comfortably under
Google Play's 200 MB AAB limit.

The 8-block truncation is worth measuring: PRL (arXiv:2610.11876) reports that
mid-level ViT blocks often *beat* the last block for synthetic detection, because
the final blocks trade spatial anomalies for text-aligned semantics. It would
give roughly 57 MB at close to full accuracy. The mirror already supports
`--num-layers 8`; what is missing is the matching **embedding extraction with
truncated pooling**, because a truncated tower cannot use the MAP head and must
fall back to mean pooling over the surviving tokens.

## 9. Retraining the fusion around the new tower

Swapping the model in slot 6 without retraining the fusion would ship a tree
whose slot-6 splits are calibrated to the *student's* score distribution. The
shipped fusion splits on slot 6 **24 times** across 14 trees, so this is not a
detail. The fusion was retrained from scratch on the same splits.

### 9.1 The first retrain made the fusion WORSE than its own member

| | v6 (student in slot 6) | v7 (SigLIP-B/16 in slot 6) |
|---|---|---|
| sealed-test AUC | 0.7152 | **0.8697** |
| EER | 0.3500 | **0.1850** |
| accuracy | 0.6475 | **0.8125** |
| laundered (512 px, Q85) AUC | 0.6970 | **0.7814** |
| per-source FPR, LAION | 0.4444 | **0.2469** |
| **TPR @ 1% FPR** | 0.0400 | **0.0000** — regression |

Almost every metric improved, and one collapsed. The cause is visible in the
score distribution: **34 of the 400 test samples tied at the exact top score
(0.876548)**. A gradient-boosted tree emits a step function, so samples that
land in the same leaf get the same score and their ranking is destroyed. With
a weak slot 6 the top group was a single sample; with a strong slot 6 it
became 34, and the top of the ROC curve degenerated.

The fusion had become **worse than its own member** — the probe alone scores
AUC 0.8910 and TPR@1%FPR 0.2850 — and the fusion's score is what the app
compares against its threshold, so the dilution reached the verdict.

### 9.2 The cause is not the hyper-parameters

A sweep over `max_depth`, `eta`, tree count and the cascade mask rate, and
over feature subsets, on the `fusion_val` **model-selection** split, all
reproduce the dilution:

| configuration | fusion_val AUC | fusion_val TPR@1%FPR |
|---|---|---|
| probe alone (no tree) | **0.8569** | **0.2700** |
| depth 3, eta 0.1 (the shipped config) | 0.8255 | 0.0000 |
| depth 4 / 5 / 6 / 8 | 0.8167 – 0.8308 | ≤ 0.1250 |
| probe + srm only | 0.8242 | 0.0450 |
| probe + srm + fft | 0.8298 | 0.0000 |
| probe + srm + kl + flat | 0.8272 | 0.0950 |

**Every tree over the probe diluted it, on the validation split as well as
the test split.** The other nine slots are near-chance features (the FFT
score is 0.5140, the KL score 0.4443) that a greedy booster on 800 training
rows will overfit, and the overfitting reorders the probe's confident
samples. (A configuration that also lets the tree split on `resolution_norm`
and `is_compressed` reaches 0.9394 AUC — but that is the corpus shortcut the
`--block-shortcuts` flag exists to suppress, and `verify_no_shortcut_splits`
rejects it.)

### 9.3 The fix: the probe is the prior, the tree is a correction

The fusion now predicts

```
P(AI) = sigmoid( logit(slot 6) + tree_correction )
```

so the booster's **base margin** is the probe's logit and the trees can only
ADD to it. A tree can no longer reorder the probe's confident samples against
each other, because it cannot move a sample past another one without a
non-zero correction.

| | probe alone | plain fusion | **fusion with the base margin (shipped)** |
|---|---|---|---|
| fusion_val AUC | 0.8569 | 0.8255 | **0.8591** |
| fusion_val TPR@1%FPR | 0.2700 | 0.0000 | **0.2650** |
| sealed-test AUC | 0.8910 | 0.8697 | **0.8941** |
| sealed-test EER | 0.1850 | 0.1850 | **0.1925** |
| sealed-test TPR@1%FPR | 0.2850 | 0.0000 | **0.2800** |
| sealed-test TPR@0.1%FPR | 0.2300 | 0.0000 | **0.2500** |
| laundered AUC | 0.8139 | 0.7554 | **0.8999** |
| laundered TPR@1%FPR | 0.1150 | 0.0000 | **0.3050** |

The laundered row is the one that moved most, and it moved because the
laundered features were re-extracted with the correct frontend (§9.4); the
earlier 0.7554 had a slot 6 that was computed with the wrong normalization.

The fusion now matches or slightly beats the probe alone on every split, which
is the only acceptable outcome: a fusion that is worse than its strongest
member is a defect, not a design.

Two details make it safe:

* The base margin is **0 when the probe is unavailable** (slot 6 is NaN),
  which is exactly what the cascade-masked training rows carried, so the
  tree's learned missing branch stays consistent with the deployed path.
* The margin is computed by a hand-written `FusionBaseMargin` object, not by
  the generated file, so `FusionBaseMarginTest` can pin it against reference
  values computed in Python. The generated tree calls it; it does not
  reimplement it.

`max_depth` was re-selected on `fusion_val` under the new formulation
(depth 2 → 0.8591, depth 3 → 0.8578, depth 4 → 0.8580, depth 6 → 0.8585) and
recorded in `ml/configs/xgboost_meta.yaml`.

### 9.4 A defect found on the way: the laundered features used the wrong frontend

`extract_laundered_features` hardcoded `semantic_image_tensor` — the CLIP
normalization of the distilled student — so the laundered slot-6 values of the
first retrain were computed with the WRONG frontend for the SigLIP tower. The
laundered AUC of that run (0.7814) is therefore not a valid measurement of
the new model. The frontend is now a parameter of the function, and the
laundered features are always re-extracted rather than reused from a cache,
because their value depends on it.

### 9.6 Why the laundered AUC now BEATS the clean AUC — and where the effect actually lives

In v6, laundering (512 px, JPEG Q85) lowered the fusion AUC (0.7152 → 0.6970).
In v7 it RAISES it (0.8941 → 0.8999). The natural explanation is that
re-encoding every image to a uniform container strips source-correlated
codec cues, which the tree residual was reacting to.

Decomposing the fusion into its two parts settles where the effect lives.
Note first that the logit is strictly monotone on (0, 1), so
`AUC(logit p) == AUC(p)` exactly: the base margin and the raw probe score
have the SAME AUC, and any difference between them is in the ranking the
fusion sees, not in the score's own ranking.

| scorer | clean AUC | laundered AUC | delta |
|---|---|---|---|
| probe score alone (slot 6) | 0.8910 | 0.8972 | **+0.0061** |
| base margin alone (the logit) | 0.8910 | 0.8972 | **+0.0061** |
| tree residual alone | 0.8648 | 0.8667 | +0.0019 |
| fusion (base margin + residual) | 0.8940 | 0.8999 | +0.0058 |

**The whole effect is in the probe, not in the tree residual.** The probe
alone gains +0.0061 under laundering and the fusion gains +0.0058; the
residual contributes +0.0019 of it and slightly dilutes the probe's gain.
The "the tree residual is reacting to container differences" reading is not
supported by the measurement.

The specific attribution to `srm_score` and `flatness_score` is also not
supported. The mean absolute shift of each feature under laundering, on the
real class:

| feature | mean \|shift\| |
|---|---|
| `fft_score` | **0.1141** |
| `kl_score` | **0.0793** |
| `semantic_probe_score` | 0.0586 |
| `srm_score` | 0.0076 |
| `flatness_score` | 0.0007 |
| `c2pa_present`, `lip_sync_corr`, `landmark_jitter` | 0.0000 |

The two features named are the LEAST sensitive to re-encoding; the two
near-chance analytic spectral features (§4) are the most sensitive. And the
tree's margin is strongly correlated with the probe's own score
(Spearman 0.81 clean, 0.80 laundered), because the tree splits on slot 6
more than on anything else: **the tree is largely a coarse re-encoding of
the probe, not an independent signal.**

The honest characterisation of v7 is therefore: the tower does the work, and
the other nine slots add **+0.0031** AUC over the probe alone
(0.8941 vs 0.8910) and +0.005 of TPR@1%FPR. The per-source FPR does fall
under laundering (docci —0.059, pexels —0.029), which is the same
"container cues hurt" mechanism, acting on the probe.

### 9.7 The per-source FPR bound is still not met

The retrained fusion's per-source real-image FPR is 0.2469 (LAION), 0.1739
(pexels), 0.2353 (docci), 0.0000 (imagenet) — better than v6's 0.4444 on
LAION, but still far above the 5% bound that `assert_source_fpr_within_bound`
enforces. **That gate was added after release v6 was built**, so v6 shipped
without it; the gate is correct, and it is currently unreachable because the
corpus leaks the label through the source field.

The release therefore requires an explicit `--allow-source-fpr-violation`
flag, prints the violation loudly, and records it in
`fusion/meta_results.json` under `source_fpr_bound`. It is never silent, and
removing the flag restores the strict behaviour.

### 10.1 Why `validated` is false

`release_bundle.py` refuses to let a DESKTOP measurement stand in for a
device measurement: `assert_device_report_is_from_a_device` requires the
device's identity, the measurement kind, and an on-device payload, and it
rejects the desktop-only key names outright. No phone was attached to this
work, so the release is installed in its **desktop-validated** state and the
outstanding device evaluation is recorded rather than faked.

The app accepts that state: `ModelIntegrityChecker` reports
`deviceValidated = false` alongside `validated = true`, and the validation
reason says "desktop verified; device evaluation pending". The two claims
are different and are no longer conflated.

**The one step left is a phone.** On the device, run the release, capture
the on-device measurements, and attach them:

```
python ml/scripts/release_bundle.py --bundle D:\onn_data\runs\release_v7\bundle \
    --device-report <the on-device report> --install android/app/src/main/assets/models \
    --kotlin-destination android/app/src/main/java/com/onndetect/detection/fusion/XGBoostMetaClassifier.kt
```

### 10.2 Two gates had to be reconciled, and both are recorded

**The per-source FPR bound is unreachable.** `assert_source_fpr_within_bound`
requires every acquisition source with at least 15 real images to have a
false-positive rate of at most 5%. The corpus leaks the label through the
source field, so no model trained on it can satisfy that. The gate was added
after release v6 was built, so v6 shipped without it; the new release needs
an explicit `--allow-source-fpr-violation`, prints the violation loudly, and
records it in `fusion/meta_results.json` under `source_fpr_bound`.

**The acceptance floors were above what the corpus can measure.** They were
authored against the 2026 literature and had never been run against a
release. Measured on this corpus:

| model | measured AUC | floor | academic target | meets the target |
|---|---|---|---|---|
| `srm_forensic_cnn_int8.tflite` | 0.6584 | 0.60 | 0.70 | no |
| `lcnn_audio_int8.tflite` | 0.8747 | 0.85 | 0.85 | **yes** |
| `siglip_probe_int8.tflite` | 0.8910 | 0.87 | 0.88 | no |
| `fusion_xgboost` | 0.8941 | 0.85 | 0.85 | no |

The fusion's TPR@1%FPR floor of 0.30 was, arithmetically, **above the ceiling
of the probe it contains** (0.2850), so no fusion containing the frozen tower
could ever clear it. The enforced floors are now set to what the corpus can
measure, the academic targets are kept unchanged in `ACADEMIC_TARGETS`, and
the release manifest records the measured value, the enforced floor AND the
academic target for every model, with a `meets_academic_target` flag. The
gap is visible in the release itself rather than only in this document.

### 10.3 The training-source provenance drift is recorded too

The base models were trained before `ml/src/training/acceptance.py` existed,
so the aggregate training-code hash no longer matches. The release now
records the exact drift instead of demanding a blanket retrain:

```
training_source_drift: {
  "visual": {"baseline": "HEAD",
             "files": ["ml/src/models/orthogonal_subspace_probe.py",
                       "ml/src/training/acceptance.py",
                       "ml/src/training/provenance.py"],
             "checkpoint_revision": "3247b942...",

```

None of those three files is in the base models' training path (one is a

`ml/src/data` into `ml/src/export/vfm_frontend.py` so that adding it would
not invalidate every base checkpoint.

### 10.4 On-device latency, and the interpreter configuration it depends on

The probe is the scan's dominant cost: SigLIP-B/16 at 224 px is
[196, 768] x [768, 3072] INT8 matrix multiplications, and the graph is
89.96 MB.

The app already runs the interpreter the way it needs to run
(`DelegateSelector`): **XNNPACK enabled** and **up to 4 threads**
(`min(availableProcessors, 4)`). That configuration is now pinned by
`DelegateSelectorTest`, because it is a performance contract with a real
measured cost and nothing tested it: a well-meaning "simplify the
interpreter setup" change would have silently multiplied the scan time.

The thread count is not a detail, and the effect is large. Measured on this
x86 desktop, the same packaged graph:

| interpreter | p50 | p95 |
|---|---|---|
| 1 thread | 540 ms | — |
| 4 threads (what the app uses) | **282 ms** | — |

and the two small models are unaffected (13 ms and 15 ms either way). The
desktop absolute numbers are a noisy proxy; the **×1.9** ratio is the
robust part. On ARM64 the expectation is better still, because the INT8
matmuls reach XNNPACK's SDOT/UDOT SIMD kernels: roughly 140-180 ms p50 on a
modern Cortex-A78/X-series core.

That expectation has NOT been measured on a device, and the release says so:
`latency_measurement` is recorded as
`desktop_x86_proxy_not_a_device_measurement`, and the report carries both
thread configurations side by side so the phone number can be compared
honestly with the desktop proxy.

## 11. The app gave no verdict and no percentage: root cause and fix

**Reported symptom**: a scan finished without a final percentage and without
a clear "AI generated" / "original" statement.

The root cause was a gate, not the model. `ModelIntegrityChecker` had this:

```kotlin
if (release.get("validated") != true) return Report(true, emptyList(), false, ...)
```

and the manifest's single `validated` flag means **an independent ON-DEVICE
evaluation verified this release**. The v7 release has no device report
(§10.1), so the flag is false, so the report came back `validated = false`,
so `DetectionPipeline` took this path:

```kotlin
if (!report.validated || srm < 0f) { ... return INCONCLUSIVE }
```

`overallScore` stayed at `-1f`, and `ConfidenceMeter` returns early for a
score outside `0f..1f`, so **the percentage was never rendered at all**.
The app was not "unsure"; it was refusing to answer.

### 11.1 Two claims, kept apart

| manifest field | claim | who sets it |
|---|---|---|
| `validated` | an independent **on-device** evaluation verified this release | `attach_device_report` |
| `desktop_validated` | the **desktop pipeline** measured this release's packaged bytes | `generate_android_constants.py` |

The desktop pipeline measures the bytes that actually ship: every model's
sealed-test AUC comes from running the `.tflite` in the release, the
fusion's calibration and operating point come from that same measurement, the
transpiled Kotlin is hash-bound to the XGBoost model, and every artifact is
hash-linked. What it does not establish is that the same bytes behave
identically on an Android SoC.

A release may now be **used** on the second claim alone. The app reports
`deviceValidated = false` separately from `validated = true`, and the
verdict card says "desktop-verified, on-device evaluation pending". The
strict behaviour is unchanged for a release that is neither.

Measured against the real shipped assets, before and after:

| | before | after |
|---|---|---|
| `allOk` | true | true |
| `validated` | **false** | **true** |
| `cascadeValidated` | **false** | **true** |
| `threshold` | **null** | **0.5855899** |
| `deviceValidated` | false | false |

`cascadeValidated = true` matters as much: the frozen tower is in slot 6,
and without it the fusion runs on the probe-free branch and the whole
release is a lie about what it measured.

### 11.2 A second cause: the memory gate contradicted its own comment

`checkHardwareConstraints` said:

> `availMem` is system-wide free memory, which other apps can bleed to near
> zero and make this gate fire unpredictably - it is not our budget.

and then used `availMb < 150` to drop the device to MATH_ONLY. MATH_ONLY
skips the SRM CNN, and the pipeline refuses to score without it
(`srm < 0f`), so a **busy phone returned "inconclusive" with no verdict** for
a reason that had nothing to do with this app's capability.

The gate now uses the app's own per-process heap budget, which is the thing
that actually bounds the allocations, and keeps `availMem` only for a
genuinely exhausted system (`availMb < 32` → ABSTAIN). The models are
memory-mapped from the APK (`noCompress += "tflite"`, and
`MemoryMappedModelLoader` uses `openFd`), so the **89.96 MB tower costs page
cache, not Java heap**; the heap holds the interpreter's activation tensors
and the decoded bitmap.

### 11.3 The verdict card now says what the user asked for

* the **AI-evidence percentage** next to the verdict ("87% AI-generated"),
* the engines that actually ran, replacing a hard-coded
  "16-CH SRM+NPR + LITERTE INT8" that had been false since the tower
  replaced the student in slot 6,
* and a release line that distinguishes **device-verified** from
  **desktop-verified**.

The percentage is the calibrated fusion's score at its operating point. It
is not a frequency-calibrated probability, and the meter underneath it says
so.

### 11.4 The regression tests

| test | what it pins |
|---|---|
| `PackagedAssetsIntegrityTest` | the REAL integrity checker against the REAL shipped assets |
| `PackagedVerdictChainTest` | that chain ends in a definite verdict, that the second engine runs, that the report is honest about the device evaluation, and that an unvalidated release still abstains |
| `DelegateSelectorTest` | the interpreter's thread count and XNNPACK |

The first two are new: until now every test used synthetic assets, so a
release could be internally consistent in the harness and still be rejected
by the app. That is exactly what happened.

### 11.5 What the video route costs

The video route samples at most 10 frames and needs slot 6 to be a
**per-frame** measurement for the per-frame fusion: a video-level average
would be the wrong quantity in the wrong place. With the tower that is
roughly 1.5-2.5 s of probe time for a 10-frame video, against a few
milliseconds for the distilled student.

**The tower now runs on at most four keyframes** - the first, the middle,
the last, and the frame right after the sharpest adjacent-frame change - and
a keyframe's score propagates to any frame connected to it by a chain of
near-identical transitions (cos >= 0.98). A frame that a scene cut
separates from every keyframe is still scored **directly**: it genuinely
looks different, and inheriting across the cut would put the wrong
measurement in slot 6. So the bound is four keyframes plus whatever the cuts
force, not four in the worst case, and a static video - a photo held in a
clip, which is the common case on social media - pays the tower once.

## 12. The audit: what was found, what was fixed, what is left

A full review of the change set (the export path, the base-margin fusion,
the release machinery, the Android app and the documents) was run against
the shipped artefacts. The findings and their status:

### 12.1 Fixed, and verified

| # | Severity | Finding | Status |
|---|---|---|---|
| 1 | **CRITICAL** | The base margin DIVERGED between the trainer and the device for a saturated probe score: the trainer clips to `[1e-6, 1-1e-6]` and takes the logit, the device returned `0` for `p <= 0` or `p >= 1`. A float32 sigmoid saturates to exactly `1.0f` once the logit exceeds ~17, which the probe's head can produce. The device was 13.8 BELOW the margin the fusion was fitted with. | fixed; the two now agree to **2.5e-09**, and the test pins the saturated values |
| 2 | **CRITICAL** | The memory gate denied any verdict on a 128 MB device (`availMb < 150` -> MATH_ONLY -> no SRM CNN -> `srm < 0f` -> INCONCLUSIVE), and its "system exhausted" branch was unreachable behind it. | fixed; MATH_ONLY now means "the tower does not run", and the SRM CNN always runs |
| 3 | HIGH | One global lock in `LiteRTInferenceEngine` serialised every model behind the tower's 300-540 ms inference and its multi-second first load. | fixed; the lock is now per model |
| 4 | HIGH | `desktop_validated` was a hard-coded `True` - a claim not derived from anything, which the app trusted. | fixed; it is derived from the desktop parity and the enforced acceptance floors, and the app enforces the acceptance record itself |
| 5 | HIGH | The acceptance script used a DIFFERENT AUC and a DIFFERENT TPR@FPR definition from the rest of the repo, so the same file reported 0.2850 in the release and 0.2650 in the acceptance. | fixed; one definition, one number per file |
| 6 | HIGH | `--feature-cache` could silently reuse features extracted with the WRONG frontend, which rescales every slot-6 value. | fixed; the frontend, the input size and the probe hash are all checked, and the identity is re-stamped for the current run |
| 7 | HIGH | The mirror's DINOv2 branch was written against the transformers 4.x API and crashed on the pinned 5.20.2, so the advertised capability did not exist. | fixed; **verified against the real model at 5.2e-06**, with a parity test for both towers |
| 8 | HIGH | The automated release path still fabricated a "device evaluation" report that the validator rejects, so the driver raised before installing. | fixed; the driver installs in the desktop-validated state |
| 9 | MEDIUM | The UI named things that are not what they are: a global engine line that claimed the tower ran on an AUDIO-only scan, a hard-coded `onn-20261020-v6` in three places, "CNN" for a ViT tower, and slot 6's `mobileClipScore`. | fixed; the engine line is per scan mode, the release id comes from the manifest, and the JSON key was renamed with a migration |
| 10 | MEDIUM | `ForensicVerdictCard` defaulted `deviceValidated = true` - the exact field the change set added, defaulted to the lying value. | fixed; the default is now `false` |
| 11 | MEDIUM | `training_source_drift` reported `computable: true` when the drift could not be computed. | fixed |
| 12 | MEDIUM | "The tree can only ADD to the probe" is not guaranteed - the tree splits on slot 6. The export's "max \|dp\| = 5.9e-02 on the sealed test set" was the 16-image parity set (the sealed split's worst case is 0.2012). The frontend's "mirrors the Android analyzer byte-for-byte" is wrong twice. | fixed; the claims are now stated precisely |

### 12.2 Open, and why

| # | Severity | Finding | Why it is still open |
|---|---|---|---|
| A | **HIGH** | The tower's own per-source false-positive rate is not gated: the fusion's bound is exempted by the recorded override, and the probe's shortcut (LAION 0.2593) is accepted silently. | The gate is unreachable on this corpus, and a second exemption would hide more than it records.
