# ML, data, export and release audit — 29 October 2026

This is a source and local-verification audit of the current checkout. Historical accuracy reports are treated as supplied evidence, not independently reproduced results. No datasets, checkpoints, shipped neural binaries, or production source files were changed. Temporary synthetic fixtures were used only to reproduce validator behavior.

## Assessment

The project has useful implementations of versioned frontends, strict dataset manifests, resumable training, labeled export parity, generated Kotlin fusion, release hash binding and device promotion. The current model release remains explicitly `validated=false`, with `device_validation.passed=false`. Those flags must stay false until real evidence exists.

The principal ML completion problem is inconsistent enforcement: newer orchestration paths and convenience fallbacks bypass several safeguards described by the repository contract. Passing implementation tests therefore does not establish that a release is reproducible, independently evaluated, or ready for detection claims.

## Findings and completion requirements

### ML-01 — High: fusion training silently overrides safety and preservation flags

`ml/scripts/train_xgboost_meta.py:544-546` unconditionally sets `overwrite`, `allow_source_fpr_violation` and `allow_manifest_drift` to true, after parsing the CLI. As a result, callers that never requested these exceptions still overwrite outputs, accept a different dataset manifest and permit source-bias violations. CLI help and the repository contract imply these actions require explicit choices.

**Complete when:** delete the forced overrides; require an explicit diagnostic flag for every exception; record it in candidate metadata; prohibit those candidates from production promotion. Add subprocess tests that use omitted flags and verify refusal before writing outputs.

### ML-02 — High: cached features are rebound to newly supplied model hashes

`train_xgboost_meta.py:591` loads the saved cache identity. At `:647-661`, `identity` is replaced with a fresh dictionary constructed from the currently supplied model files. The cache checks at `:667-678` then compare this new identity to the same current files. They no longer compare the original cached model/baseline/frontend identity. With a matching dataset hash, stale features can be labeled as if they came from a replacement model, and the new identity is saved at `:750`.

**Complete when:** preserve immutable `cached_identity` and separately compute `expected_identity`; compare model, frontend, baseline, feature-source/schema and split identities before using any cached row. Bind each scored sample ID and label to the verified manifest. Test model replacement, baseline replacement, preprocessing changes and reordered split membership.

### ML-03 — High: release validation can skip the very metrics needed for acceptance

`release_bundle.py:240-242` skips model acceptance if an evaluation entry lacks a nested `test` dictionary. The shipped `evaluation_report.json` uses flat `test_auc`, `tpr_at_fpr_1pct` and `tpr_at_fpr_0_1pct` fields, so this is the format currently in use. The fallback manifest checks compare AUC and a declared AUC floor; they do not enforce the missing sensitivity gates. `:261-265` likewise only gates fusion when a test dictionary exists.

`release_bundle.py:168-175` accepts a boolean `passed` and any numeric agreement in `[0,1]` plus any nonnegative max error. It does not enforce the actual numeric parity limits from `validate_export.compare_scores`. The adversarial temporary fixture passed with agreement zero and max error 999.

The low-FPR sample-size requirement is relaxed with `require_low_fpr_statistic=False` for both base and fusion models, even when `require_validated=True`. A phone report therefore does not by itself strengthen the statistical release gate.

**Complete when:** one versioned evidence schema requires complete metrics for every shipped detector and deployed fusion, with class/group counts, frozen threshold and numeric export bounds. Reject missing sections. Make pilot staging distinct from distribution eligibility, including the required real-example count. Recompute acceptance from trusted measurements rather than trusting a `passed` flag or arbitrary manifest floors.

### ML-04 — High: pipeline writes or replaces dataset lineage rather than proving it

`run_track4_fusion_release.py:390,396` loads SRM/SigLIP evaluation artifacts without checking the expected visual manifest. At `:405-407` it overwrites both calibration split hashes with the current dataset hash. This makes previously measured calibration appear to belong to a different corpus without re-running it.

`generate_android_constants.py:170-176` similarly replaces an unrecognized semantic-probe split hash with the visual dataset hash. Its flat-report fallback also substitutes default TPR values at `:216-217`, turning missing measurements into values.

The shipped report already contains a visible inconsistency: SRM `n_calibration` is **300** in `evaluation_report.json` and **400** in `constants/release_manifest.json`, while the model/frontend identities otherwise refer to the same asset.

**Complete when:** foreign or missing hashes fail; calibration is rerun on an explicit declared pool; provenance from the measurement is immutable. Require exact matching threshold, AUC, counts and split hashes across report/manifest/constants. Missing metrics stay unavailable and cannot qualify acceptance.

### ML-05 — High: a second packaging path mutates Android source and bypasses transactional install

`run_track4_fusion_release.py:298-304` copies the generated Kotlin classifier into production Android source **even when `install_to_repo` is false**. A staging run therefore changes the compiled classifier independently of packaged assets. Its optional install at `:584-605` then copies model files, constants, fusion files and reports sequentially into live assets, without the rollback transaction supplied by `release_bundle.py`.

The CI training workflow selects this track-four route by default. Duplicate pipeline entrypoints thus have different safety guarantees.

**Complete when:** all routes produce a self-contained candidate only; a single validated install transaction replaces matching Kotlin and assets together, preserving/rolling back the previous version. Candidate generation must leave Android source and assets unchanged. Test interruption after each install step.

### ML-06 — High: high-resolution data builder does not establish its claimed ancestry/revision contract

`build_genimage_highres_dataset.py:54-58` obtains the latest revision or substitutes `"a" * 40` after an API error. The `load_dataset` calls at `:63-67` do not pass the recorded revision. Numeric labels are accepted directly at `:80-85`, without semantic class-name verification. `group_id` is derived from re-encoded JPEG bytes at `:134`, then `grouping_verified=true` is asserted at `:168`.

Exact byte deduplication only proves that identical encoded blobs are absent. Crops, recompressions and other descendants of the same original can have different hashes; a content hash is not authoritative original-image ancestry. Counter/quota assignment of val/calibration/test does not create generator-independent holdouts.

**Complete when:** require an immutable supplied revision and pass it to every read; fail on missing revision or semantic labels; preserve original source IDs/groups and generator metadata; group descendants before splitting; add near-duplicate/source auditing. Use separate destinations instead of dataset replacement for release preparation.

### ML-07 — High: independent fusion splits and source evidence can silently disappear

If stacking/fusion_val are absent, `train_xgboost_meta.py:688-693` divides the base detector's `val` pool into fusion training and fusion validation. That validation data already influenced base-model selection, so it is not the independent stacking contract described in `CLAUDE.md`. The required-independent-stacking configuration is not enforced by this fallback.

When test records cannot be resolved, `:913-916` invents `test_group_i` and `test_source`. This manufactures apparent independent groups. The source-FPR checker in `training/evaluation.py:80-83` treats missing source axes as an empty set and returns without a violation. The current fusion report has `groups={}` and `source_fpr_bound.enforced=false`.

**Complete when:** refuse absent independent splits and missing ancestry/source records; require a minimum auditable source coverage to claim the source gate passed. An unavailable subgroup analysis must remain explicitly unmeasured and block the applicable release claim.

### ML-08 — High: headline low-FPR ranking does not describe the installed operating threshold

The shipped fusion report records a threshold of **0.5781998634**, clean **FPR 0.055** and laundered **FPR 0.065** on 200 real examples. The reported TPR@1%FPR values of 0.94/0.90 describe other points on the test ROC curve, not the frozen deployed threshold. The clean FPR Wilson interval is approximately **3.1%–9.6%**. The 0.1% FPR statistic is based on only 200 real examples, below the project's own minimum of 2,000.

The fusion report also evaluates continuous scores, while runtime cascade abstention may change the distribution of completed assessments. End-to-end sensitivity, false-positive rate, abstention rate and coverage must be measured together for the exact deployed policy.

**Complete when:** select the operational threshold using calibration against the product's false-positive objective; freeze it; report actual sealed-test TPR/FPR and confidence intervals, plus cascade coverage. Use larger independent real pools and group-aware uncertainty. Keep ROC ranking metrics separate from operational claims.

### ML-09 — Medium: current Android assets fail the strict bundle verifier

The manifest's exact asset set omits `trust/c2pa_trust_anchors.pem`. The strict bundle verifier rejects the real asset tree before the model/evidence checks. This is a real integration gap even if the narrower lineage script or another Android gate passes.

**Complete when:** explicitly bind the provenance trust store and all other security-relevant runtime assets in the release contract. Update all validators and packaging routes to share the same inclusion policy; do not simply ignore unmanifested assets.

### ML-10 — Medium: acceptance helpers permit nonfinite metrics

`training/acceptance.py:94-99` accepts Python numeric values without checking finiteness or `[0,1]`. Comparisons such as `nan < min_auc` evaluate false; a direct temporary check accepted NaN AUC and both NaN TPR metrics with 4,000 real examples.

**Complete when:** reject booleans, NaN, infinity and out-of-range values; require strict nonnegative integer counts; prohibit nonstandard NaN JSON output. Add boundary tests to the helper and full release validator.

### ML-11 — Medium: local corpus and research evaluation cannot reproduce production comparisons

The locally available `datasets/openfake_visual/dataset_manifest.json` identifies `dragonintelligence/CIFAKE-image-dataset`, revision `local-desktop-slice`, with 400 train / 200 val / 200 calibration / 200 test records and hash `fbab1565b7a2494cc2434ca18134f713280e27143a1ddcc6d5668a41459c6853`. The shipped release declares visual hash `940bedf7412f383be7ed6f2f425b6208b02cf7de29f66bc3a37386ce9aa17505`. These are different datasets; historical accuracy cannot be reproduced from the local slice.

`evaluate_qwen_probe.py:66-125` silently downloads a small CIFAKE slice when split directories are missing, without an immutable revision. It interprets source label zero as real, whereas `fetch_local_eval_slice.py:43-44` explicitly documents the reverse mapping for that same source. At minimum, the two paths have contradictory semantic contracts. Qwen/Gemma discovery also accepts directory fallbacks without validating the strict manifest/hash/group-disjointness contract. Their comparison tables use hardcoded historical baseline metrics rather than scoring all candidates on the same exact examples.

**Complete when:** require a named verified evaluation manifest and immutable model revisions; verify semantic label names once; reuse that manifest across all candidate and baseline runs; include checkpoint, embedding-cache, sample and environment hashes. Keep tiny procedural/CIFAKE smoke fixtures separate from forensic accuracy evidence.

### ML-12 — Medium: configured dual-engine orchestration does not register its optional model

`run_training_pipeline.py:82-83` calls `export_all_models.py` without its existing `--cascade-tflite`/frontend options, creating a manifest with only the required base models. At `:88-100` it then exports or copies the optional probe into `bundle/models`, and uses it for fusion, but never adds its tensor contract, parity/calibration/sealed-test report or model hash entry to the release manifest. `generate_android_constants.py` only attaches cascade metadata if the optional model is already in the manifest. The strict bundle validator therefore sees an unmanifested model; the semantic exporter also creates a sidecar that needs an explicit artifact policy.

**Complete when:** wire the optional probe through the authoritative export stage so it receives the same report and lineage contract as the base models. Add an orchestration integration test that builds small valid optional-probe fixtures and verifies the resulting bundle and source/asset consistency. Avoid maintaining a separate copy-only route.

## Work order to reach a defensible release

1. **Restore evidence integrity first:** remove forced overrides; repair cached identity comparison; prohibit lineage rewriting and default measurements; centralize staging/install. These changes protect subsequent expensive training work.
2. **Define the product operating contract:** image/document/speech/video support, acceptable FPR/recall/coverage, abstention, supported codecs, transformations and target phones. Set thresholds before final sealed evaluation.
3. **Prepare auditable data:** immutable licensed sources, verified labels and authoritative ancestry; independent train/val/stacking/fusion_val/calibration/test; source-balanced authentic controls; leave-generator/source/language/speaker holdouts; social recompression and partial edits. Require enough real examples for low-FPR estimates.
4. **Train one reproducible baseline:** archive effective configs, resolved environment, source snapshot, checkpoints and data manifests. Select on val, fit fusion on stacking, select fusion on fusion_val, calibrate once and evaluate sealed test once.
5. **Qualify exact exported bytes:** score the packaged graph and generated Kotlin with matched data; enforce numeric and task parity, including missing slot 6, probe/base disagreement, compression, resizing and audio resampling. Add actual cascade outputs to the sealed report.
6. **Measure phones:** independent native decode/preprocessing parity, exact release hashes, first-run offline behavior, per-modality latency percentiles, peak memory, sustained/thermal behavior, cancellation and error recovery. Qualify recording-level/video aggregation separately.
7. **Promote and publish evidence:** strict complete bundle gate, signed distribution, truthful model card and benchmark report. Keep unsupported tasks and research modules diagnostic until their own data and acceptance criteria pass.

Adding more model families before steps 1–3 increases experimental volume without closing the current release gaps. The existing image/speech baseline should first become independently reproducible and measurable.
